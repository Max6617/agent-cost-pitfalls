Do this once per terminal window, before anything else. $env:DSH_HOME is set for processes DSH launches, not for your own PowerShell window. Without it, every command below that uses it resolves to C:\.agent-presets\... and fails with PathNotFound. That was the cause of a real failure during setup.

if (-not $env:DSH_HOME) { $env:DSH_HOME = Join-Path $HOME '.dsh' }

3 · First live run of the router 10 minno keydo this first

Do parts A, B and C below, in order — they are one action split into three.

Part A on its own does nothing except switch a log file on. The point of this section is to make the router run once and prove it works. The router is the only thing built here that has never executed, and everything downstream — the decision-model comparison, the cache claim — depends on it working. Free, and needs no API key.

A. Switch the ledger on. It ships off, so nothing is recorded by default.

$f = "$env:DSH_HOME\.agent-presets\ptc-router\agent.cordis.yml"
$ledger = Join-Path $env:USERPROFILE 'router-ledger.jsonl'
(Get-Content $f -Raw) -replace 'ledgerPath: null', "ledgerPath: $ledger" |
  Set-Content $f -Encoding UTF8
node tools/validate-presets.mjs

With no argument it defaults to $DSH_HOME/.agent-presets and derives the module search paths itself, so it works even when DSH_HOME is unset. Pass a directory to check somewhere else; a bad path now prints a one-line message instead of a stack trace.

Verified end to end: the exact commands above were run, the resulting path was checked with the same dirname/appendFileSync calls the router makes, and the preset still validated. The file is only created once the router runs.

Validation must still say all modules resolve. If it does not, restore with scripts/harness.ps1 presets -Force.

B. Start a NEW session, pick PTC + router, and give it a real task.

A running session cannot change preset — that is enforced by DSH, not a limitation of this setup. And a preset only applies to sessions started after the change.

C. Check whether it actually routed.

Get-Content "$env:USERPROFILE\router-ledger.jsonl"
node tools/dsh-audit.mjs

Expect ledger lines of kind input, inject, route, and an audit route: line matching what the router chose.

You are done with this section when the ledger file exists and contains at least one input line. That single fact proves the decision layer loads inside a real session.

Why the gateway is what makes this fair

Six harnesses have different defaults for model, reasoning effort, autonomy and retries. Comparing them raw measures the defaults, not the design. The gateway forces model and effort to be identical across arms and logs every rewrite, so a harness that asked for something else shows up in the results instead of hiding. 9 · Decision model optionalno hardware

You said no hardware purchase — that rules out CLM's reference setup. CLM needs vllm serve, and vLLM requires CUDA. Your machine (i7-1260P, 15.7 GB RAM, Intel Iris Xe 1 GB) has none. So the realistic options are CPU-only CLM, hosted Jev, or skipping it. Skipping is a defensible choice — see 9d.

Understand what you would be buying before buying it.

Jev (TypeSafe)CLM-8B (Stanford+NVIDIA)
licencecommercial, hostedApache 2.0
shapehosted API75 MB head over frozen Qwen3-8B
costper callfree at the margin once served
accuracybetternot better on any published row — ties on games, trails 95.2% vs 99.2% on BFCL v4 tool calling

Read the "up to 9×" claim carefully: it comes from one row (a game, 16.5 vs 149.8 ms). The other rows are 1.6×–4×. And that game number measures a combined system — a physics planner labels actions in the prompt and a safety shield replaces unsafe answers.

The number that should shape your paper.

CLM's DeepSWE 81.6% is 31 of 38 tasks — and on 25 of those 38 the verifier's choice could not change the result. Independently, the routing literature finds only 29 of 294 questions were improvable by routing at all. Two unrelated sources agree: decision models only matter on a minority of decisions. That is your framing, and it is why the router gates on ambiguity instead of routing everything.

If you try CLM anyway, on CPU.

pip install contrastive-lm

The reference path (vllm serve) will not run. The in-process engine accepts any OpenAI-compatible embeddings server, which is the only CPU route:

python -c "from clm import Engine; e = Engine(emb_url='http://127.0.0.1:PORT/v1/embeddings'); print(e.rank('What causes tides?', ['The Moon pull','Photosynthesis','The Earth is round']))"

Serve Qwen3-8B as embeddings from Ollama or llama.cpp. Untested caveat: CLM expects the encoder in a specific pooling mode and a CPU server may not reproduce it exactly. Expect 1–10 s per decision on this CPU versus 16.5–80 ms on a 4090 — usable once per user input, unusable per step.

If you use Jev or CLM, wire it as an exempt client.

node tools/measure-gateway.mjs --port 8787 --log results/gateway.jsonl `
  --force-model deepseek-flash --force-effort high `
  --exempt clm `
  --upstream-for clm=http://127.0.0.1:8700
This is why --exempt exists. Model enforcement is what makes the harness comparison fair — but applying it to a decision model would rewrite the decision model's own model and destroy the measurement. Exempt clients are still attributed, logged and priced; they are just never rewritten.

Then swap decide() in router/router-core.mjs for the model call on the weak band only. The ledger and the cache-safety guard keep working unchanged.

The hypothesis, which is narrow and cheap.

The deterministic core already gets 87% of frontier quality at 56% cost with no classifier call at all. So the question is not "is a decision model better" but:

> Does a decision model beat keyword heuristics on the ambiguous band only — the inputs the router sends to weak — by enough to pay for its own latency and tokens?

Arms: ptc-opt (no decision layer) vs ptc-router (deterministic) vs ptc-router+model (weak band delegated). A negative result is as publishable as a positive one.

Troubleshooting

A preset shows as broken in the picker

DSH lists broken presets with a reason naming the rows at fault rather than hiding them. Run node tools/validate-presets.mjs "$env:DSH_HOME\.agent-presets" — it parses every composition and resolves every plugin row, including relative ./x.mjs paths. Restore with scripts/harness.ps1 presets -Force.

scripts/harness.ps1 refuses to apply the patch

It detected a DSH host listening on port 3080. The profile is patchReload: live, so applying would reload it mid-session. Stop DSH first, or pass -Force if you accept the reload.

The gateway exit-codes complaining about DEEPSEEK_API_KEY

By design — it refuses to start rather than forwarding synthetic keys upstream. Set $env:DEEPSEEK_API_KEY, or pass --allow-unauthenticated for a local smoke test only.

The patch merge refuses to run

Your patch file contains !!js expressions. Re-emitting YAML would flatten those into plain strings, so the merger refuses and tells you to merge by hand. That is the safe outcome, not a bug.

A harness will not talk to the gateway

Check in order: (1) is it using the /v1 suffix, (2) does it accept a custom base URL at all, (3) does it need the Responses API rather than chat completions — the gateway bridges that at /v1/responses for Codex-style clients, (4) does it refuse non-HTTPS or non-OpenAI hosts. If none work, record it in notes/records/CROSS-HARNESS.md section 2 and drop the arm.

The router runs but nothing appears in the ledger

ledgerPath is still null. See Part A of section 3. (Regenerating presets now preserves a ledger path you have set, so it survives scripts/harness.ps1 presets -Force.) Also confirm you are in a new session — presets cannot change mid-session.

I want to go back to the version without any of this

git checkout v0-baseline in the workspace, and restore the DSH side with Copy-Item snapshots\v0-baseline\agent-presets\* "$env:DSH_HOME\.agent-presets\" -Recurse -Force. The live profile patch was never modified, so nothing else needs undoing.
